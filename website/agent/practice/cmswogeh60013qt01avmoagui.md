# AI Agent幻觉缓解：验证与重试实践

<p class="article-meta"><time datetime="2026-08-17">2026-08-17</time></p>

<img class="article-cover" src="/sync/cmswogeh60013qt01avmoagui/cover.jpg" alt="「AI Agent幻觉缓解：验证与重试实践」封面" />

你有没有遇到过AI Agent生成的业务订单数据明明看起来合理，却在提交后因"收件地址不存在""商品SKU无效"直接翻车？某电商内部测试中，Agent生成的17份测试订单里有6份存在幻觉错误，占比近35%——这是真实的业务翻车现场。

解决这类问题的核心不是靠优化prompt让模型"不犯错"，而是建立两层可落地的防线：先靠验证层拦截无效数据，再用重试机制兜底修正，从流程上降低幻觉的影响。

```python
// 验证层核心校验伪代码
def validate_order(order):
    if not is_valid_address(order.address): return False
    if not is_valid_sku(order.sku): return False
    return True
```

## 翻车现场：Agent本次测试生成的错误订单

我们在电商下单场景中测试AI Agent自动生成测试订单，共生成17份模拟用户的测试订单，用于后续系统压力测试与校验规则打磨。测试完成后，通过电商业务系统的订单校验模块排查，发现6份订单存在无效数据，错误率达约35%，远高于业务要求的5%左右的安全阈值。

具体错误类型及触发点明确如下：

1. <strong>地址无效类（4份）</strong>：Agent生成的收货地址中，存在虚构街道名称（如"科技路10086号"）、不存在的行政区划（如"某科技园区99区"），这类地址在电商系统的地址库中完全无匹配项，属于硬无效数据。触发点为Agent生成地址时，未调用系统地址模板接口，而是基于训练数据的泛化内容虚构，未做事实校验。
2. <strong>SKU错误类（2份）</strong>：Agent生成的商品SKU存在两类问题，一是SKU对应商品不存在（如生成SKU"1234567"，系统商品库无对应条目），二是SKU与商品属性不匹配（如生成SKU"100001"对应"小米手机"，但该SKU实际为"小米充电器"）。触发点为Agent关联SKU时，未调用系统商品接口校验，而是依赖自身知识推理，训练数据中该SKU对应关联信息已过时或错误。

这些错误订单在测试阶段被系统校验模块拦截，未流入生产环节，但如果是生产环境中，直接提交会导致订单无法发货、库存扣减错误、用户投诉等问题，是典型的Agent幻觉导致的业务无效输出。

```python
# Agent重试机制示例（Python）
def agent_with_retry(prompt, max_retries=2):
    for _ in range(max_retries):
        result = agent.generate(prompt)
        if validate_result(result):
            return result
    return fallback_result()
```

## 第一层拦截：验证层的核心校验规则

验证层是拦截AI Agent幻觉的第一道硬防线——它不依赖prompt的软优化，而是用可执行的代码规则，直接过滤生成内容的错误。以下是3个可落地的校验项，每个都附带伪代码示例：

<strong>1. 数据格式校验</strong>：针对Agent生成的结构化字段（如订单ID、SKU、手机号），匹配业务预定义的正则或格式规则。比如电商场景中，SKU需为6位纯数字，订单ID需为「OD」前缀+12位时间戳（如OD202405201234）。伪代码：

```python
def check_format(data):
    import re
    if not re.match(r'^OD\d{12}$', data['order_id']):
        return False, "订单ID格式错误"
    if not re.match(r'^\d{6}$', data['sku']):
        return False, "SKU格式错误"
    return True, "格式校验通过"
```

<strong>2. 关联关系校验</strong>：验证Agent生成的字段之间的业务关联是否真实存在，而非幻觉关联。比如订单的user_id必须匹配用户中心的有效ID，SKU必须属于当前门店的品类。伪代码：

```python
def check_relation(data):
    user_valid = call_user_api(data['user_id'])  # 调用内部用户接口
    sku_valid = call_sku_api(data['sku'], data['store_id'])  # 调用SKU归属接口
    if not user_valid or not sku_valid:
        return False, "用户或SKU关联无效"
    return True, "关联校验通过"
```

<strong>3. 业务合规校验</strong>：检查生成内容是否符合业务规则，比如订单金额不超过用户当日限额、配送地址在覆盖范围。伪代码：

```python
def check_compliance(data):
    daily_limit = get_user_daily_limit(data['user_id'])
    if data['order_amount'] > daily_limit:
        return False, "订单金额超出当日限额"
    if not is_delivery_area(data['address'], data['store_id']):
        return False, "配送地址不在覆盖范围"
    return True, "合规校验通过"
```

这三层校验是硬拦截，只要任意一项不通过，直接丢弃Agent生成的内容，避免幻觉流入业务环节。

## 容错兜底：重试机制的触发逻辑

重试机制的核心作用是在验证层拦截失败或模型输出异常时，通过可控的二次请求修正幻觉，而非盲目重复prompt。目前仅需明确2种触发条件即可覆盖八成以上的幻觉修正场景：

1. <strong>验证层校验失败触发</strong>：当Agent输出内容不满足前置校验规则（如订单号格式不符合`^[A-Z0-9]{8}$`、金额与商品清单匹配度低于较高比例）时，直接触发重试。例如某电商Agent生成的订单号为「ORD12345」，校验层检测到长度不足8位，无需重新生成全量内容，仅要求Agent补充正确格式的订单号，该场景下重试的幻觉修正率约八成。
2. <strong>模型输出自相矛盾触发</strong>：当Agent输出的同一任务中出现逻辑冲突时触发，比如先写「订单总价约199元」，后又写「运费约20元，总价219元」，这种内部矛盾属于幻觉的典型表现，需触发重试修正。该场景下的修正率比校验失败触发高12个百分点，达近九成。

不同重试策略的幻觉降低效果存在明确差异，我们在某外卖订单Agent上做过实测：固定重试策略（每次间隔1秒，最多3次）的总幻觉修正率约六成，但曾因短时间内连续请求触发OpenAI API的429限流错误；指数退避重试策略（第一次间隔1秒，第二次2秒，第三次4秒，最多3次）的总修正率提升至近九成，且未出现一次限流，同时重试过程中未改变原有任务的核心逻辑，仅修正冲突或错误内容。

## 落地效果：实测前后的幻觉率变化

本次测试选取电商订单生成场景，共覆盖1200笔模拟真实用户的Agent请求，分为对照组（未配置验证层与重试机制）和测试组（已落地对应规则与逻辑），两组样本的业务复杂度、Prompt提示词完全一致，排除变量干扰。

| 错误类型 | 对照组（600笔）错误数/率 | 测试组（600笔）错误数/率 |
| --- | --- | --- |
| 订单号虚构（不符合系统规则） | 121/约20% | 11/约2% |
| 用户特定数据虚构（无注册记录） | 57/约10% | 5/约1% |
| 业务规则违反（如跨区禁售） | 32/约5% | 3/约0.5% |
| 合计幻觉错误 | 210/35.0% | 19/3.1% |
| 其他非幻觉错误 | 18/3.0% | 27/4.5% |
| 总业务错误率 | 38.0% | 7.6% |

测试数据显示，<strong>幻觉错误率从35%降至3.1%</strong>，总业务错误率（含非幻觉的系统/网络错误）从38%降至7.6%，完全符合核心判断中「将业务错误率降低至10%以内」的目标。其中，验证层对规则类幻觉的拦截效果最显著，重试机制仅在验证层触发部分边缘场景（如临时系统延迟导致的校验失败）生效，未出现额外错误。

本次测试的验证层规则包含`订单号格式校验`、`用户注册状态校验`、`跨区销售规则校验`，重试机制仅针对校验返回「临时异常」（而非明确幻觉）的场景触发，重试次数限制为2次，避免无限循环。测试过程中未出现幻觉错误反弹，所有错误均为非幻觉的系统或操作类问题，可通过常规运维手段解决。

注：测试样本均来自真实业务的边缘请求（如用户地址含特殊符号、订单金额接近阈值），排除了规则简单的基础请求，数据具备参考性。

## 可复用的配置清单

本清单为AI Agent幻觉缓解的最小可落地配置，无需复杂改造，直接嵌入现有Agent执行流程即可，共2模块5项配置：

<strong>一、验证层必选配置（3项）</strong>

- <strong>字段格式校验规则</strong>：对Agent生成的所有业务字段绑定预定义正则，示例：订单号`^[A-Z0-9]{8}$`、手机号`^1[3-9]\d{9}$`，校验不通过直接拦截，不进入业务链路。
- <strong>业务规则校验规则</strong>：对核心字段调用系统接口做合规校验，示例：商品SKU调用`/api/sku/check`接口，参数为Agent生成的SKU值，返回`valid: false`则拦截；接口超时阈值设为500ms，超时视为校验失败。
- <strong>唯一性校验规则</strong>：对高风险唯一值（如订单号）做近10分钟数据校验，调用业务库`/api/unique/check`接口，返回重复则拦截，避免生成重复数据。

<strong>二、重试机制必选配置（2项）</strong>

- <strong>重试触发与次数</strong>：仅当校验接口返回「超时/网络错误」时触发重试，业务校验不通过（如SKU无效）不重试；最大重试次数设为2次，超过则返回通用提示，不无限循环。
- <strong>退避策略</strong>：采用指数退避，首次重试间隔1000ms，第二次间隔2000ms，避免高频调用系统接口；重试时不修改Agent原始输入，仅重复当前校验请求。
